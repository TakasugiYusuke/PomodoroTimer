# Focus Flow 無料公開・通知検証計画

## 1. 結論

Focus FlowをHTTPS対応の静的ホスティングへ配置すれば、通常利用時に`start.cmd`は不要になる。利用者は公開URLをブラウザで開き、初回だけ通知を許可すればよい。

第一候補は、既存リポジトリ`TY-ama/PomodoroTimer`を利用したGitHub Pagesとする。

- 想定URL: `https://ty-ama.github.io/PomodoroTimer/`
- 公開方式: `main`ブランチの`/(root)`を直接公開
- ビルド処理: なし
- サーバー処理: なし
- 費用: 公開リポジトリでGitHub Freeを利用する場合は無料
- `start.cmd`と`server.js`: ローカル開発・障害切り分け用として残す

## 2. GitHub Pagesを選ぶ理由

現在のアプリはHTML、CSS、JavaScript、画像、Service Workerだけで構成された静的サイトであり、GitHub Pagesの用途に合致する。リポジトリのリモートも既にGitHubへ設定されている。

GitHub公式ドキュメントでは、ビルド工程が不要なサイトはブランチからの直接公開が推奨されている。公開元にはブランチのルートまたは`/docs`を指定できる。本プロジェクトは`index.html`がルートにあるため、`main`の`/(root)`が最も単純である。

### 代替候補

| 候補 | 採用判断 | 用途 |
|---|---|---|
| GitHub Pages | 第一候補 | 既存GitHubリポジトリから最短で公開する |
| Cloudflare Pages | 第二候補 | リポジトリを非公開のまま無料公開したい、またはプレビュー環境が必要な場合 |
| Netlify / Vercel | 今回は見送り | 将来ビルド処理やサーバー機能を追加する場合に再検討する |

Cloudflare Pagesの無料枠は静的アセット配信が無料で、Freeプランでは月500ビルド、1サイト20,000ファイルまで利用できる。本アプリの規模では十分だが、GitHubとの追加連携設定が必要になるため今回は第二候補とする。

## 3. 公開前の前提条件

- GitHub Freeで運用する場合、対象リポジトリをPublicにする。
- リポジトリ内に公開してはいけないAPIキー、パスワード、個人情報がないことを確認する。
- デフォルトブランチ名を確認する。本計画では`main`を想定する。
- GitHub上でリポジトリの管理権限を持つアカウントを使用する。
- 通知のテストにはWindows上のChromeまたはEdgeを使用する。

GitHub Pagesのサイトはインターネットへ公開される。リポジトリが非公開でも、対応プランで公開したPagesサイト自体は公開になるため、機密情報を含めない。

## 4. 実装計画

### フェーズ1: 公開用ファイルの準備

1. ルートへ`.nojekyll`を追加し、静的ファイルをそのまま配信することを明示する。
2. `index.html`、`app.js`、`stylesheets/`、`img/`、`sw.js`が相対パスだけで参照されていることを確認する。
3. Service Workerの登録先が`./sw.js`であることを確認する。
4. READMEへ公開URLと、`start.cmd`はローカル起動専用であることを追記する。
5. JavaScript構文チェックとローカルサーバーでの疎通確認を行う。

GitHub PagesのプロジェクトURLには`/PomodoroTimer/`というサブパスが付く。現在の相対パス構成なら、アセットとService Workerのスコープはこのサブパス内に収まり、そのまま動作する見込みである。

### フェーズ2: GitHub Pagesの有効化

1. GitHubで`TY-ama/PomodoroTimer`を開く。
2. `Settings`を開く。
3. 左メニューの`Pages`を開く。
4. `Build and deployment`の`Source`で`Deploy from a branch`を選ぶ。
5. Branchに`main`、Folderに`/(root)`を選ぶ。
6. `Save`を押す。
7. GitHub ActionsのPagesデプロイが成功するまで待つ。
8. 表示された公開URLを開く。

このフェーズはGitHub上の設定変更を伴うため、実施時はリポジトリ管理者が操作する。

### フェーズ3: 公開環境の通知検証

以下をWindowsのChromeとEdgeでそれぞれ確認する。

1. 公開URLがHTTPSで表示される。
2. 開発者ツールのApplication画面で`sw.js`がActivatedになっている。
3. 画面の「ブラウザ通知を有効にする」を押す。
4. ブラウザの通知許可で「許可」を選ぶ。
5. 「テスト通知をWindowsへ送信しました」と画面に表示される。
6. Windowsのトースト通知、または通知センターにテスト通知が表示される。
7. 最短の区間を設定し、別タブへ移動した状態で区間終了通知が届く。
8. 通知をクリックするとFocus Flowのタブへ戻る。
9. 再読み込み後も設定と通知許可が維持される。

`file://`と公開URLは別のオリジンとして扱われるため、これまでローカルファイルに付与した通知許可は引き継がれない。公開URLで改めて許可する。

### フェーズ4: ドキュメントと運用の確定

1. README先頭付近へ公開URLを掲載する。
2. 通常利用は公開URL、開発・オフライン確認は`start.cmd`と明記する。
3. 更新は`main`へのpush後に自動反映される運用とする。
4. デプロイ失敗時はGitHubの`Actions`タブでPagesの実行履歴を確認する。
5. 公開を停止する場合は`Settings > Pages`からUnpublishする。

## 5. 合格条件

次の条件をすべて満たしたら公開完了とする。

- 公開URLへアクセスするとFocus Flowが正常表示される。
- CSS、Material Icons、favicon、JavaScriptに404がない。
- `sw.js`が公開URL配下で有効化される。
- 通知許可後、テスト通知がWindows通知センターへ届く。
- タブがバックグラウンドでも区間終了通知が届く。
- 通知クリックで既存タブが前面に戻る。
- タイマー、プリセット、テーマ、音量保存に回帰不具合がない。
- `start.cmd`を使用せず、公開URLだけで通常利用できる。

## 6. 制約と注意点

- ホスティングしても、タイマー処理自体がサーバーで動くわけではない。タイマー実行中はブラウザでページを開いておく。
- PCがスリープしている間は、区間終了時刻どおりにJavaScriptを実行できない。復帰後に遅れて処理される場合がある。
- Windowsの「応答不可」や集中モード、ブラウザ単位の通知無効化が有効な場合、API送信に成功してもトーストが見えないことがある。
- ブラウザのサイトデータを削除すると、通知許可やService Worker、localStorageの設定が消える場合がある。
- URLが変わると通知許可は引き継がれない。カスタムドメインへ移行する場合も再許可が必要になる。

## 7. ロールバック計画

公開後に問題が見つかった場合は、次の順序で切り戻す。

1. GitHub PagesをUnpublishして新規アクセスを止める。
2. 不具合のあるコミットを打ち消すコミットを作成する。
3. ローカルで`start.cmd`から回帰確認する。
4. 修正版をpushし、Pagesを再公開する。

履歴を破壊する`git reset --hard`や強制pushは使用しない。

## 8. 実施見積もり

- 公開準備: 10〜15分
- GitHub Pages設定と初回デプロイ: 5〜10分
- Chrome / Edge通知検証: 10〜15分
- README更新と最終確認: 5分

合計の目安は30〜45分とする。
